# 0017. A verification runner runs one verification kit; the method does not change with the project

- Status: Proposed
- Date: 2026-10-10

## Context
The method of Zephyros is the same for every project: requirements with their verification methods, stories and criteria linked to them, results recorded by the hub, a gate of fixed rules ([0005](0005-deterministic-acceptance-gate.md)). What changes from one project to another is how the delivered code is started and observed. A library is verified by its tests. A web application needs its tests and a browser that reads the page. A simulation is compared with a reference scenario, within tolerances. Infrastructure code is verified by its plan and by policy checks. A Minecraft plugin needs a server and a bot that plays. All of these run delivered code, so all of them run in the sandbox ([0004](0004-sandboxed-execution-of-delivered-code.md)).

## Decision
- A **verification runner** is a public interface of the hub (CTR-11), versioned, with a dummy implementation and a conformance suite. Given a tree to verify, the acceptance tests to run and a kit, it starts the project, observes it, and returns one outcome per acceptance test (passed, failed, error, not run), with bounded evidence (a log excerpt, and files such as screenshots). It renders no decision.
- A **verification kit** is the part that changes: how to start the project and how to observe it. A kit is an image and a contract between the runner and that image (where the tree is, how the tests are named, where the outcomes and the evidence are written). The configuration of a project names its kit.
- The first kit is **tests**: the project's test runner (pytest first). The second is **tests and a headless browser**: the same, plus Playwright reading the page and taking screenshots as evidence. Later kits (simulation, infrastructure, Minecraft with MockBukkit, a headless Paper server and a Mineflayer bot) add an image and a contract, and change nothing in the gate.
- Subjective checks stay human, at the demonstration: no kit judges taste or intent.
- The runner of the hub runs every kit in a sandbox created through the container filter: no network, no secret, limits, destroyed at the end.

## Consequences
- Positive: the gate, the evidence report and the traceability are the same for every kind of project.
- Positive: a new kind of project is a new kit, written and tested on its own against the conformance suite.
- Negative: each kit image is something more to pin, build and keep up to date.
- Negative: a kit decides how outcomes are written, so a kit must keep them out of the delivered code's reach (EXG-37, ATK-22), and that constrains how its acceptance tests are written (for the "tests" kit, black box — see below).

## Result integrity (EXG-37, ATK-22)

**The promise.** The outcome a kit records reflects the real execution of the tests, whatever the delivered code does.

**Why the first design did not hold.** The "tests" kit used to print a signed outcome line: a nonce, then the outcomes with an HMAC under that nonce, checked by the filter. The delivered code ran in the same interpreter as the tests (an acceptance test imported it, e.g. `from calc import add`). The audit of 2026-10 showed the signature bought nothing there: the nonce and the outcomes were attributes of the kit's own module, so a delivered module imported by a test did `sys.modules["zephyros_kit"].OUTCOMES = …` and read `_NONCE` — a plain attribute access — and the kit then signed the forgery itself. This is not specific to one trick: **any code that runs in the process that records the outcome can rewrite that outcome before it is recorded.** A signature protects a message against another process; it does nothing against code in the same process. Canaries do not close it either — the Contractor reads the contract, so it can tell a canary (a test no criterion names) from a real test and spare it while forging the rest.

**The decision.** The only sound fix is that **no delivered code runs in the process that records the outcomes.** The "tests" kit enforces it:

1. **No delivered import into the judge.** Before pytest collects anything, the kit installs an import barrier (a meta-path finder) that refuses to import any module resolved under `/work` other than the exact acceptance-test files asked for. A module is judged by where it is listed *and* by where it really is, so a link made in the tree to a file written elsewhere is a delivered module like any other. An acceptance test is therefore **black box**: it runs the delivery as a subprocess and reads its output; it may not `import` the delivered code into the judge. A test that tries to import it fails to load and is an error, never a pass. The run also ignores the project's own configuration and conftests (`-c /dev/null`, `--noconftest`) and keeps the working directory off `sys.path` (`python -P`).
2. **The judge is not debuggable.** `prctl(PR_SET_DUMPABLE, 0)` makes the judge's memory unreadable to the unprivileged subprocesses a black-box test spawns, whatever `kernel.yama.ptrace_scope` is on the host, so a child cannot recover the nonce by attaching to its parent.
3. **The signed line tells the judge apart from those children.** A black-box test's subprocess shares the container's stdout — the log the filter reads — and the framework echoes what a failing test's subprocess wrote into that log, after the kit's signed line. The nonce lands only there (write-only from inside the container) and never in a child's memory or environment, so a child can write a line but cannot sign one. The filter believes the outcomes only when it has read the whole log, which begins with the run line, and exactly one run line and one matching signed line are present; a second line (a child's forgery) makes the run an error. The log has to be read whole because the run line is what anchors the signature: a delivery that wrote more than a tail window and ended with a pair of its own would otherwise leave that pair as the only one. A log longer than the filter reads (16 MiB), or that does not begin with the run line, is not believed. Two hub canaries that must fail, and the time limit, are kept as a backstop: a run whose canary did not come back failed, or that was stopped, is not believed.

**Attack surface reviewed.** What the delivered code can reach is the judge's imports, its configuration, and — through the subprocesses a black-box test runs — the container itself. A subprocess is the same user as the judge and as the container's init process, so it can write to the container's log (by the echo of a failing test's output, or through the init process's descriptor, `/proc/1/fd/1`), and it can signal the judge. Each way below has an end-to-end test in `tests/runtime/test_sandbox_runner_conforms.py`, unless said otherwise.
- *A delivered module imported by a test* (the audit's attack: rewrite the kit's outcomes, read its nonce) — blocked: the import fails and the test is an error. So is the same module forging from an `atexit` handler or monkeypatching the framework: both need the module to be imported into the judge first. So is a module a subprocess has linked into the tree during the run, for a later test that still imports the delivery.
- *A bytecode cache shipped next to an asked test file* — the judge would run it in place of the source whenever the time and size it records match (the tree is extracted with a fixed time, and the size of a file is a guess away): the kit removes every `__pycache__` of the tree before it collects anything.
- *A `conftest.py`, a `pytest.ini`, a plugin the delivery names* — never loaded (`-c /dev/null`, `--noconftest`). *A file named like the kit plugin* — inert (`python -P`). *The manifest* (`zephyros-request.json`) rewritten by the delivery — the kit reads it once, before any delivered code runs.
- *A subprocess reading the judge* (memory, environment, descriptors) — refused: the judge is non-dumpable. It never learns the nonce, and cannot write through the judge's own stdout.
- *A subprocess writing lines to the log* — it cannot sign them, and a second pair makes the run an error. *A flood that pushes the kit's lines out of a window to leave a pair of its own as the only one* — the filter reads the log whole, so the kit's run line, the first of it, is there to make the pair a second one. *A subprocess that writes such a pair and then kills the judge* — same: the pair is a second one, and a judge that ends without printing its line leaves nothing to believe (`not_run`).
- *A judge that is killed or dies* (`SIGKILL`, `SIGTERM`, tested; the out-of-memory killer ends it the same way) — it prints no line, so nothing is believed. *A judge that is interrupted* (`SIGINT`, tested) prints its line with no result for the test it was running, which reads `not_run`. In none of these does the running test read as passed, and a run whose canaries did not come back failed is refused.
- *Environment variables* — the container's are fixed by the filter's template and the image; the delivery sets none of the judge's.

**Honest limits.**
- Acceptance tests of the "tests" kit **cannot import the delivered code**. A library is exercised as a subprocess (`python -c "from lib import f; print(f(…))"`), not with `from lib import f` in the test. Owner support modules imported by a test are blocked for the same reason, and so is a package marker (`__init__.py`) of a directory of tests: an acceptance test must be a self-contained file, or black box. This is a real change in how the kit is used.
- The acceptance-test **files themselves run in the judge**, so they must be the Owner's, held by the hub. A delivery that could place its own file at a path a criterion names would run in the judge and could forge. Keeping delivered files out of that set is the hub's job (the delivery loop refuses a delivery that changes an acceptance test), not the kit's.
- The barrier and `PR_SET_DUMPABLE` are the load-bearing boundary; they hold on the Linux kit image. The signature, the whole-log reading and the canaries are layered on top, not the primary guarantee.
- A delivery shares the container's log with the judge, so it can always make a run **unreadable** — flood it past 16 MiB, write lines that look like the kit's — and so turn any verdict into an error. That is a denial of verdict, never a pass. The container runtime must keep the whole log of a sandbox: one that rotates container logs can cut the head of a flood, and the filter then refuses the log unless the cut falls exactly on a run line the delivery wrote. Sandbox logs should not be rotated, and a sandbox that floods its log still costs disk until its time limit: this design does not bound that.
- `VerificationResult.deselected` (interface 0.2.0) lists the tests the kit found in the asked files but did not run for want of a criterion, so the report can say which acceptance tests never ran; it is part of the signed payload, so it is authenticated like the outcomes.

## Alternatives considered
- One runner per kind of project, each with its own notion of a result: the gate would have to know every kind.
- Letting the Contractor provide the verification scripts: the Contractor never verifies (EXG-08).
- Collecting the outcomes in a parent process so the nonce never enters the judge at all (the preferred shape of EXG-37). It is a worthwhile hardening, but it does not change the trust boundary: if delivered code ran in the judge it could still feed the parent a consistent forgery (canaries and all), so the barrier is needed regardless. Kept as a possible later refinement; the barrier is what makes the current design sound.
- Allowing imports but detecting forgery with canaries only: defeated by the Contractor, which reads the contract and spares the canaries.
