# Zephyros 0.2.0

Version 0.2.0 fixes what two independent audits of 0.1.0 found, keeps instances off the open
Internet by default, and changes the verification kit so that delivered code cannot forge its
results. It is still an experimental release for one machine, Linux or macOS with Docker.

The [CHANGELOG](../../CHANGELOG.md) lists every change with the pull request that made it. This
page says what changes for someone who runs Zephyros.

## Breaking changes

**Acceptance tests are black box.** The `tests` kit no longer lets an acceptance test import the
delivered code: a delivered module imported into the process that records the results could
rewrite them (ATK-22). A test now runs the delivery as a subprocess and reads its output:

```python
import subprocess
import sys


def test_add() -> None:
    out = subprocess.run(
        [sys.executable, "-c", "from calc import add; print(add(1, 2))"],
        capture_output=True,
        text=True,
        check=True,
    )
    assert out.stdout.strip() == "3"
```

A test that does `from calc import add` fails to load and reads `error`. So does one that imports
a support module of its own, or a package marker (`__init__.py`) of its directory: each test file
must stand alone. Keep the expected values in the test file (see the limits below).

**Instances reach the hub and the package registries, not the Internet.** The default level of
network access is `regulated` ([ADR 0024](../decisions/0024-three-levels-of-network-access.md)):
an instance reaches the hub and, on port 443, the hosts of `network.allowed_hosts` (by default
`pypi.org`, `files.pythonhosted.org`, `registry.npmjs.org`; not GitHub) through an egress proxy in
the hub, which logs every destination. `sealed` reaches the hub alone. For the behavior of 0.1.0,
set `egress = "open"` in `[network]`, or `ZEPHYROS_EGRESS=open` for `scripts/deploy.sh`. The
instance image now carries pytest, so a `sealed` instance can run its tests.

**No PASS without evidence.** A delivery is CONCERNS at best when the contract has no requirement
or constraint, or when no acceptance test of the judged objects ran and passed; the report says
nothing was judged. A contract judged by inspection alone no longer reaches PASS.

**The importer refuses instead of guessing.** `contract.import` takes a document whole or not at
all. An identifier defined twice, a verification method that is not T, I, A or D, and a
requirement row without its five cells are refused, with their line.

**Notifications carry more values.** `delivery.decided` is now sent for every declared delivery,
including `REFUSED` and `ERROR`; the alerts of the continuity ladder can carry
`side: main-agent`. A receiver that checks these fields against a closed list must accept the new
values.

## What else changes

- **The Contractor no longer reads the Owner's test code** through `delivery.status`: its report
  leaves out the output of the run and keeps every per-test outcome. The Owner side, the operator
  and the main agent read the whole report.
- **A named acceptance test file the hub does not hold is never taken from the delivery.** It is
  reported missing, its tests are `not_run`, and the report and the log name it.
- **The report names the Owner's tests that never ran**, because no criterion names them.
- **The main agent is sent every documented event**, `delivery.reviewed` included, once and in
  order, from a queue the hub sends on a thread of its own: a slow receiver no longer freezes the
  hub. A notification that fails is logged, not sent again (see the limits).
- **The continuity ladder survives a restart of the hub**, waits until the contract is ready
  before it wakes the Contractor, and alerts the main agent, then the human, when a change the
  Owner side proposed waits for a decision.
- **The model policy is the configuration.** The code no longer locks the gateway to one model:
  `gateway.models` lists what it may send.
- **The log anchor no longer turns itself off.** A missing or unreadable anchor fails
  `log.verify`; keep the anchor with the database in a backup.
- **Masking leaves ordinary words alone** (`risk-management-module` stays as written), and a
  branch whose name looks like a credential is refused at the push.
- **Errors through MCP carry their corrective action**, as on the operator channel
  ([error messages](../errors.md)).
- **A recorded run can be replayed** with the tools in `tools/replay/`
  ([replay format](../replay-format.md)).

## Known limits

- One machine, IPv4 only. Linux and macOS; not Windows. On macOS the CI runs the unit and
  acceptance suites only; the runtime suite and the real runs were on Linux.
- One verification kit, `tests` (pytest, Python 3.12). Instances run Python 3.14: a test that
  depends on the minor version of Python may behave differently there.
- The Owner's other files in the sandbox (reference data, helper scripts) can be rewritten by the
  delivered code before a test reads them. The kit holds the test files themselves to what the
  hub sent; keep the expected values inside them.
- A delivery can make its own verification unreadable, which ends in an error, never in a pass.
- The Contractor still reads the names and outcomes of the tests, the names and digests of the
  Owner's files, any test the client keeps in its own repository, and, if it can reach the forge,
  the full report on the pull request.
- At `regulated`, an allowed registry is still a channel for data, and the proxy does not make it
  read-only; installing a package runs the registry's code in the instance. `open` reaches the
  whole Internet.
- A client that ignores `HTTPS_PROXY` reaches nothing, but leaves no record in the hub's log. No
  ceiling bounds the tunnels an instance opens, and refusals of the proxy do not count toward
  `limits.refusals_per_minute`.
- Notifications are sent once, without retry. The queue holds 1,000; what is queued when the hub
  stops is logged as `hub_stopped` and not sent. After an outage of the receiver, read the log.
- A contract that names no acceptance test starts no continuity ladder for the Contractor; one
  named test is enough to wake it, even between two proposals of the contract.
- The log anchor is a file next to the database: whoever can write the hub's data directory can
  forge both. A lost anchor keeps the log verification failing; there is no re-anchoring yet.
- Not built yet: approvals signed by the human, budgets, a dashboard, backups, previews, and the
  automated delivery checks for vulnerable dependencies and committed secrets (EXG-35).
- The three runs with real models used 0.1.0 and earlier code, with an agent in the operator's
  place. The changes of 0.2.0 are covered by the test suites, not yet by a real run.

## How to update

```bash
scripts/deploy.sh down            # stops the hub and the filter; the volumes stay
git fetch --tags && git checkout v0.2.0
uv sync --locked
scripts/deploy.sh up              # with the same variables as before
```

Before you start the new version:

1. **Rewrite the acceptance tests as black box**, as above. A test kept by `acceptance.put`
   is the file the hub runs: put the new version.
2. **Choose the network level.** Instances that need GitHub or another host either get it in
   `network.allowed_hosts` (port 443 only, one name per host) or run at `open`.
3. **Update the receiver of the notifications** if it checks `decision` or `side`.

When it starts, the hub stops every guard made by 0.1.0 (it carries no level), with the turn it
may be running; the instance keeps its volumes, and its next turn starts at the configured level.
The records of deliveries and the log need no migration; the hub adds its table of continuity
tasks itself.
